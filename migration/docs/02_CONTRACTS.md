## C. Time contracts

**C.1 Clocks.** MySQL `NOW()` / `CURRENT_TIMESTAMP` = start of the
*statement*, whole seconds. PostgreSQL `now()` = start of the *transaction*
(constant across a transaction — measured), `statement_timestamp()` = start
of the statement (advances — measured), `clock_timestamp()` = wall clock
inside a statement. The port maps **`NOW()` → `portal.now_s()`** and
**`NOW(3)` → `portal.now_ms()`**, both `date_trunc(…, statement_timestamp())`,
so the semantics are MySQL's inside and outside transactions.
`CURRENT_TIMESTAMP` in `routes/notifications.js:398,427` is the same mapping.

**C.2 Rounding vs truncation.** A `timestamptz(0)` column **rounds** a
fractional input (`…:00.600` → `…:01`, measured; MySQL rounds too for a
`DATETIME(0)` cast, measured) while `NOW()` never carries a fraction.
`portal.now_s()` truncates first, so a stored stamp is never later than the
instant it describes. The one place this matters is the restore cutoff:

**C.3 Same-second cutoff.** `middleware/auth.js` and `socket.js` reject a
token when `decoded.iat * 1000 < new Date(token_valid_after).getTime()`.
With a truncated whole-second cutoff, a token minted after the write in the
same second is accepted and a token minted one second earlier is rejected
(both measured). Had the cutoff been rounded up, a legitimate same-second
token would be rejected (measured as the counter-example). `iat` is whole
seconds by the JWT spec; the confirmation stamps (`email_verified_at`,
`contact_verified_at`) are whole seconds; "confirmed since this sign-in" is
`floor(stamp/1000) >= iat` — unchanged (rehearsed).

**C.4 Zones.** `timestamptz` stores an instant. The session `TimeZone`
changes only the *text* rendering (`08:39:44+00` vs `16:39:44+08`,
measured); pg hands the API a Date, `res.json()` prints UTC, as mysql2 did.
The transfer reads MySQL in `time_zone='+00:00'` and appends `+00:00`;
mysqldump's `--tz-utc` does the same for the snapshot. The source host's
zone (UTC+8) therefore never enters a stored value. **The API host's
`process.env.TZ` no longer matters for stored values**; it still matters
for `todayLocalDateString()` and the school calendar, which are
deliberately local-date computations in the client and `format/`.

**C.5 Clock skew between API host and database host** becomes an input:
the cutoff and the "since sign-in" rule compare an API-minted `iat` with a
database `portal.now_s()`. Tolerance is under one second; `06` §4.4 measures
it on the hosted pair before cutover.

**C.6 Intervals and differences.** `NOW() - INTERVAL ? MINUTE` →
`portal.now_s() - make_interval(mins => $1)`; `TIMESTAMPDIFF(SECOND, a, b)`
(truncating) → `floor(extract(epoch from (b - a)))::int` — a plain `::int`
cast **rounds** (59.9 → 60, measured) and would shorten the 60-second resend
cooldown by up to a second.

**C.7 The seven ON UPDATE behaviours** (trigger vs MySQL, all measured
side by side): real change bumps (both); no-op UPDATE does not bump (both;
mysql2 reports `affectedRows 1, changedRows 0` under its default
`FOUND_ROWS` flag, pg `rowCount 1`); NULL→value bumps (both); value→NULL
bumps (both); an explicit `SET updated_at = …` wins (both); upsert hitting
the same values does not bump (both; MySQL `affectedRows 1`, pg `rowCount 1`);
upsert changing values bumps (both; MySQL `affectedRows 2`, pg `1`); upsert
insert path (`1` on both). **No application branch reads `affectedRows`
after an upsert**, so the 2-vs-1 difference is inert (`03` lists every
`affectedRows` reader).

**Decisions (the first three are settled; the fourth is open):**

1. **Equality, UNIQUE, joins and grouping on the nine key columns use
   `portal.ci`** — the only candidate that reproduces MySQL's
   case-and-accent-insensitive equality, which the sign-in path depends on
   (`routes/auth.js:73` `WHERE u.login_id = ?` with the typed id, and
   `loginThrottle.loginKey()` lower-casing the same id — the design assumes
   case-insensitive ids). Verified end to end in `rehearse.js`
   (`signin.lowercase_login_id_matches`, `assignments.duplicate_with_case_variant_section_is_23505`,
   `settings.upsert_case_variant_updates_same_row`).
2. **Trailing-space equality is not reproduced** (`abc` ≠ `abc `). The
   source holds no padded value (01 §2), every write path trims
   (`String(x).trim()` in auth, users, students, settings) and the port adds
   nothing; a `WHERE login_id = ' x'` that MySQL would have matched now
   misses — acceptable and documented, not silently different.
3. **`LIKE` on a `portal.ci` column is replaced** (two sites: `users.js:405`
   `login_id LIKE ?` and nothing else — `students.js:130` and
   `messages.js:235` search default-collation name columns): on PG 17
   `login_id COLLATE "C" ILIKE $1` (measured working, `rehearse.js`
   `users.ILIKE_with_explicit_C_collation_works`); on PG 18 the native
   `LIKE` could return. **Read on 2026-10-24 through the read-only MCP
   (D-70): the project runs PostgreSQL 17.11, so the `COLLATE "C" ILIKE`
   form stands; re-read before cutover in case the platform moves to 18.**
4. **Accent-insensitive search is a gap** (`nino` no longer finds `Niño`;
   measured). MySQL gave it for free; `ILIKE` gives case only. Options:
   `unaccent(expr) ILIKE unaccent($1)` (extension available locally,
   `rehearse.js` `students.search_with_unaccent_extension`; Supabase ships
   `unaccent`), or accept case-only search. Learner names in this school
   do carry ñ. **Owner's decision; the port inventory carries it as item
   Q-12.** **Decided — the owner's Q5 (b), 2026-10-25, built in Phase 3
   commit F: no extension; ONE fold in `config/db.js`** (`foldedSql` /
   `foldedContains`: NFC, `lower()` under the ICU root collation `und-x-icu`,
   one `translate()` of the accented Latin letters; the term folded the same
   way in JavaScript). **Measured in commit 7** (`semantics.js` section G,
   against MySQL's `utf8mb4_unicode_ci LIKE` on the new scratch): equal on
   case and Latin accents (`nino`→Niño, `jose`→JOSÉ and back, `PENAFLOR`→Peñaflor,
   `ñ`→Ñoño, `ána`→Ana, a no-match control); the fold also finds `lukasz`→Łukasz,
   which MySQL does not; MySQL finds full-width `Ａｎａ` and `İsmail`, which the
   fold does not; `strasse`→straße neither. The cluster-dependent part
   (normalize + ICU `lower()`) gives identical text on the local cluster
   (17.10, ICU collversion 153.14) and the hosted one (17.11, 153.121), so
   the hosted search folds as the local one does.
5. `citext` was measured and **not chosen**: case-only equality, no accents,
   no normalization; it would also change every column's type and break
   the `portal.ci`-keyed UNIQUEs' accent behaviour. `lower()` indexes:
   same limits plus a rewrite of every predicate.
6. **Ordering**: MySQL's case-insensitive order on name lists becomes
   `C`-order (uppercase first) under the database default. Visible in sorted
   tables (Admin → Users by name). The sort-only candidate `und-u-ks-level1`
   *deterministic* collation gives `A,a,Á,á,B,b,z` without affecting
   equality or LIKE; it was recommended for the `ORDER BY name` expressions
   (a `COLLATE` in the pagination allow-list), to be decided with Q-13.
   Supabase's database default is `en_US.UTF-8` (libc), which orders
   `a,A,á,Á…` — different from both; the hosted check records it.
   **Decided — D-2 below (the owner, 2026-10-25: D-135 Q5, reaffirmed in
   D-141): the database default stays; no `COLLATE` is added to any sort.**
